M6 — Move history & undo

revision 3 · mockup for approval · nothing here is live

M6 is the milestone where Accept finally moves the file. Two things follow from that. The popup has to show that work is happening and, when it fails, stay open and say why — sections 4 and 5. And every move has to be written down somewhere you can find it and take it back — the new History pane in Settings, sections 1 to 3.
The Light / Dark toggle at the top stays on screen as you scroll — flip it in any section. Every drawing is labelled with when you would see it.

What changed since revision 2 — and why

  1. You reversed the dropdown decision on 28 July, and this whole mockup follows. Revision 2 turned the menu-bar dropdown into a floating panel so it could hold history rows and buttons. You chose the conservative option instead: the dropdown keeps its current style and changes nothing visually. Every panel drawing from revision 2 is deleted.
  2. Move history and Undo now live in the Settings window, in a new History tab. This is a better home than the dropdown, not a consolation prize: a window has no menu constraints, so rows can be multi-line, honest about failure, keyboard-reachable and readable aloud by VoiceOver — none of which the dropdown could do.
  3. The dropdown gets exactly one change, and it is behavioural. A file row whose suggestion is ready becomes clickable and re-opens that file's popup. It looks like an ordinary menu item, because it is one. Section 6.
  4. The popup keeps the anatomy you approved in M5 — same width, same lines, same proportions — and gains three states: Moving…, failed, and folder-blocked. Sections 4 and 5.
  5. Four notes from the last review are fixed: system colours instead of hand-picked ones, a recommendation on the small grey text, a footer that can no longer jump, and a rule that stops one successful move reading as two separate events. Section 7.
Unchanged

The menu-bar dropdown

Same style, same look, same rows as today. No history section, no Undo, no buttons on the right, no outcome lines. One behavioural change only: a row with a ready suggestion is now clickable and brings its popup back.

When you see it Settings › History, a normal week in. Six of the last 34 moves are visible; the list scrolls. Two of these can still be undone, and only those two carry a button.
  • Three lines, always in the same order. Line 1 is the name the file has right now — that is what you would type into Spotlight. Line 2 is what happened. Line 3 is where it came from, or what to do next when something went wrong. Every state uses the same three slots, so your eye learns one shape.
  • Undo appears only where undoing is genuinely possible. Two rows here have it; four do not. A row that cannot be undone says so in words — it is never a greyed-out button, because a greyed-out button invites you to hunt for a way to enable it.
  • Only the button is clickable. The row itself is inert. Undo cannot be redone in M6, so there is deliberately no big target to hit by accident, and no confirmation dialog to train you to click through.
  • Day headers instead of a date on every row. “Today”, “Yesterday”, then the weekday and date. The row keeps just the clock time, which is all you need once you know the day. VoiceOver still reads the full “Moved today at 11:04”.
  • Long names are cut in the middle, so the extension always survives: acme-invoice-final-FIN…ned(3).pdf. Hovering shows the whole name, and the whole name is what a screen reader reads — the app never stores a shortened one.
  • Amber means your file is fine but something did not go to plan. Red means it did not happen. Both are always full sentences, so the meaning survives with the colour removed.
  • The list holds the last 200 moves (your locked decision) and scrolls. Nothing expires on a timer — a move from three weeks ago is still undoable if the file is still where the app left it.
Founder decision — where History sits among the tabs I have put it third: General · Folders · History. General first is the macOS convention, and Folders is the thing you set up once. History is the thing you visit when something surprised you, which is rarer than it feels. My recommendation: leave it third. Say the word if you would rather History came second, since after M6 it is arguably the more interesting pane.
Founder decision — the new name is on top, the old name underneath The popup shows the old name first and the new name below it, because at that moment you are deciding about a file you still think of by its old name. The history reverses that: the file's current name is line 1 and “was …” is line 3, because by then you are looking for a file you now know by its new name. My recommendation: keep the reversal. The alternative — printing old → new on one line — reads well with short names and falls apart with two long ones, and it overloads the arrow, which everywhere else in this app means “into this folder”.

  • “Unknown” is a real answer, and it gets a real row. The tempting thing is to hide these or guess. Both are worse: hiding one means your history is quietly incomplete, and guessing means the app might offer an Undo that moves the wrong file. So the row stays, says what it does not know, and tells you the two places to look.
  • Row 8 is the fail-closed rule made visible. Your locked decision was that if the undo record cannot be written, the file is not moved. This row is where the user finds out that nothing happened — and why that was deliberate.
  • Row 6 keeps its Undo on purpose. The move genuinely happened, so the record is still true; only this attempt to reverse it failed. If you put the file back where it was, Undo will work. The app never goes hunting across the disk for a moved file — it looks exactly where it left it and reports honestly when it is not there.
  • No row is ever deleted to tidy up. Rows leave only by falling out of the 200-move window, or when you clear the history yourself.
  • For the builder: every one of these is one accessibility element reading as a single sentence — “2026-06 Acme invoice.pdf. Moved to Invoices, today at 11:04. Was acme-invoice-final-FINAL-v3-signed(3).pdf.” The folder glyph and any arrow are decoration and must be hidden from VoiceOver.
Founder decision — should “Moving…” rows appear at all? Row 3 only ever shows if you happen to have Settings open at the exact moment a move runs, which is a fraction of a second in normal use. I have kept it because the alternative is a row that pops into existence fully formed, and because a slow copy to an external disk is exactly when someone would go looking. My recommendation: keep it.

The fix, shown. Even handed an absurdly long status string, the footer stays one line high and the buttons stay put — the caption truncates instead of wrapping. In revision 2 that same string wrapped to two lines and shoved the buttons down at the exact moment you clicked one.
Moving…
What actually ships. The in-flight caption is the single word Moving… in every case, in every language. Anything longer to say goes on its own line above the footer, like the slow-disk sentence.
  • Hide, not Cancel — and the word matters. Once the disk has started a move the app cannot call it back, so it must never show a button that looks like it can. “Hide” describes exactly what the click does. It also carries a tooltip and a spoken hint: “The move continues. The result appears in Settings › History.”
  • Esc is never inert. Esc = Hide during a move, Esc = Dismiss everywhere else. There is no state in this app where pressing Esc does nothing.
  • Nothing jumps. The footer swaps in place over about 120 ms and the panel keeps its size. A surface that resizes at the moment you click reads as an error even when it is not one.
  • The spinner is delayed by about 200 ms. Almost every move finishes faster than that; a spinner that flashes on and off looks like a glitch, which reads as failure. Accept disables immediately either way, so a second click cannot start a second move.
  • No progress bar, no percentage. A same-disk move is a single instruction to the disk — a bar would be theatre. An indeterminate spinner is the honest shape for “working”.
  • The 15-second auto-dismiss is cancelled the instant Accept is pressed, so the panel can never vanish on its own while it is holding a file mid-move. The next queued suggestion waits its turn.
  • Reduce Motion: no spinner at all (a spinner cannot be stopped), and the footer swaps instantly. The word “Moving…” carries the state on its own.
Founder decision — the slow-disk sentence The third panel adds one line after three seconds. It costs a line of height and a small growth animation, and it answers the only question anyone has at that moment: is this stuck? My recommendation: keep it. If you would rather the panel never changed size at all, we drop it and the spinner carries the whole story — say so and it goes.
Worth knowing — where the result goes if you hide the panel Nothing is lost by hiding. The move finishes and turns into a row in Settings › History, with its Undo. That is the whole point of building the history first: the panel is allowed to be dismissible precisely because it is no longer the only record.

7 · Colour, readability, and the four notes left over from the last review revised

Four things were flagged last time and not fixed. All four are answered here. One of them is a judgement call I would like you to look at with your own eyes rather than take my word for.

1 · Amber and red now come from macOS, not from me

Revision 2 used two colours I picked by hand. If someone switches on Increase Contrast in macOS, a hand-picked colour does not change and stays exactly as hard to read as it was. The app now asks the system for its own red and orange, which macOS darkens automatically. The amber also had almost no margin, so it sits a touch deeper — the same warm colour, easier to read.

Measured against the window background: amber 4.7 → 5.2, red 4.9. The bar is 4.5. Colour is never the only signal — every one of these lines is a full sentence that still means the same thing in black and white.

Look closely and you will notice something: in light mode those two are hard to tell apart. That is not a mistake — it is the honest consequence of using the system's colours. The bright amber macOS shows on a button is far too pale to read as 11 px text, so Apple's readable orange is a deep burnt one that sits close to red. In dark mode they separate cleanly. Flip the toggle and compare.

macOS's standard “secondary” grey measures about 3.9 against a bar of 4.5 at these sizes. That grey was carrying real sentences — “Moved to Invoices”, “Undone — back in Downloads”. Rather than darken everything and end up with a wall of black text, I have split it by what the line is for:

4 · One successful move, one place it appears

The old drawing showed a completed move twice: still sitting in the dropdown's file list, and in the history. The rule now is one sentence: the dropdown lists files that are in Downloads. A moved file is not in Downloads, so it leaves the dropdown, and its record is in Settings › History. Section 6 shows the before and after.

A failed move is not an event — nothing happened to the file — so a failed file keeps its dropdown row and stays clickable for a retry, and also gets a history row explaining why it did not happen. Those are two different statements, both true, and they are the only case where one file is visible in both places at once.

Founder decision — how dark should the small text be? Three honest ways to answer the 3.9-versus-4.5 finding. (a) Darken everything: fully compliant, but the History pane becomes a block of uniform black text and the two-second glance gets slower, because nothing stands out. (b) Leave it all grey: prettiest, and macOS does darken it for anyone who turns on Increase Contrast — but at default settings the sentences that matter most stay below the bar. (c) What I have drawn: darken the lines that report a consequence, leave the background detail grey. My recommendation: (c). It fixes the lines where being hard to read would actually cost someone something, and it keeps the hierarchy that lets you find the answer in a glance — which is itself an accessibility property, not just a pretty one. Look at the History pane in section 1 and tell me if it feels too heavy.
Founder decision — amber and red look alike in light mode Because both come from macOS, the readable orange is a deep burnt one and it sits close to red at 11 px (dark mode separates them fine). Three ways to go. (a) Leave it: the words carry the meaning, and “Renamed in Downloads — Receipts isn't there any more” could not be mistaken for a failure by anyone reading it. (b) Pick a hand-mixed amber that separates better — but then it stops responding to the Increase Contrast setting, which is the thing we just fixed. (c) Drop amber from the history rows altogether and use ordinary black text, keeping red for genuine failures — on the argument that “renamed in place” is a success with a caveat, not a warning, and colouring it warning-orange overstates it. My recommendation: (a) now, and (c) is the one I would revisit if you find yourself squinting at the pane in real use. What I will not do is (b).
Deliberately out of scope — the popup's old-name line The small grey line at the top of the popup showing the file's current name measures exactly the same. I have not touched it: that panel is your approved M5 design, it is the one in the demo video, and its greyness is doing real work — it is what makes the new name below it read as the answer. My recommendation: leave it and revisit it as its own small change after M6 ships, when you can judge it on its own instead of buried in a milestone.
  • For the builder, in one line: status colours must be the semantic system colours — .systemRed and .systemOrange — never the hex codes printed in this file. The hexes exist only so this page renders in a browser. macOS adjusts system colours under Increase Contrast; a hex does not.
  • Also for the builder: the shortened filenames in every drawing here are cut by the layout, not by the text. The app must always hold the whole name and let the label do the trimming. Building a shortened string in code destroys the real name for VoiceOver, which would then read “2026-06 Chase Sapp… tement dot pdf” out loud.
  • Every amber and red state is a full sentence that still makes sense with the colour removed, so all of this works with Differentiate Without Color switched on.
  • No custom background on the dropdown. It keeps the system menu material so that Reduce Transparency turns it opaque automatically.
